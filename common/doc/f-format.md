# Specification: HDL File Manifest Format (`.f`)

**Document Title:** Specification for FPGA/ASIC File Manifests (`.f`)  
**Version:** 1.2  
**Status:** Proposed  
**Target Domain:** FPGA and mixed-language IP repositories

Tool capability requirements in this document use the feature names listed by
`[features] allowed_features` in
[`tool_capabilities.ini`](../../tool_capabilities.ini). The capability file is
processed from top to bottom; an unknown requirement is a parse error.

## 1. Overview

The `.f` file is a small, human-readable manifest for one compile family of an
IP. It records source order, synthesis sources, named testbench source
closures, tool requirements, and portable waveform views.

The current repository already uses this pattern at paths such as:

```text
axis_fifo/scripts/vhdl.f
axis_fifo/scripts/uvvm.f
axilite_io/scripts/sv.f
axi_monitor/scripts/vhdl.f
```

The revised format keeps that layout. A single manifest may contain several
named testbenches. Separate manifests remain valid when the design family is
materially different, such as `axilite_io/scripts/vhdl.f` versus
`axilite_io/scripts/sv.f`.

### Core rules

1. File order is compile order.
2. `[rtl]` is shared by synthesis and simulation when present.
3. `[top]` is synthesis-only when present.
4. A simulation-only manifest may omit both `[rtl]` and `[top]`; each
  `[tb:<name>]` section must then contain its complete source closure.
5. Each `[tb:<name>]` section is one complete simulation target.
6. The command line selects the testbench with `--tb <name>`.
7. Wave views are portable signal declarations; simulator-specific commands
   are generated by the backend.
8. Standards are explicit and are never silently promoted.
9. Tools run in dedicated build directories inside the active IP.
10. Testbench `requires` values use the capability feature tokens from
  `tool_capabilities.ini`; an empty value means no additional requirement.

## 2. Repository Layout

The manifest remains under the IP's `scripts/` directory:

```text
sub/fpga-ip/
  axis_fifo/
    rtl/
    tb/
    scripts/
      vhdl.f
    README.md
  axilite_io/
    rtl/
    tb/
    scripts/
      vhdl.f
      sv.f
```

The canonical runner remains the repository launcher:

```text
# Windows
run axis_fifo vhdl modelsim
run axis_fifo vhdl modelsim --tb basic
run axis_fifo vhdl modelsim --tb uvvm gui
run axis_fifo vhdl modelsim --tb uvvm project

# Vivado: batch/non-project, GUI, and explicit project mode
run axis_fifo vhdl vivado
run axis_fifo vhdl vivado batch
run axis_fifo vhdl vivado gui
run axis_fifo vhdl vivado project

# XSim: batch/non-project and GUI
run axis_fifo vhdl xsim
run axis_fifo vhdl xsim batch
run axis_fifo vhdl xsim gui

# Linux
./run.sh axis_fifo vhdl modelsim --tb basic
./run.sh axis_fifo vhdl vivado
```

The command has two independent selectors:

```text
run <ip> <manifest> <tool> [--tb <testbench>] [mode]
```

`mode` is optional and defaults to `batch`. Supported modes are:

| Mode | Meaning |
| --- | --- |
| `batch` | Compile and run without opening a GUI; this is the default. |
| `gui` | Run with the tool's GUI and waveform viewer when supported. |
| `project` | Create or open the tool's native project, then run in project mode. |

The requested mode must be listed in the selected tool's `modes` value in
`tool_capabilities.ini`. `project` is distinct from `gui`: a GUI run need not
create a persistent native project, while project mode explicitly does so.
The backend determines the project format and project-specific behavior.
Vivado supports all three modes. XSim currently supports `batch` and `gui`
only; XSim project mode is not part of the current capability profile.

`<manifest>` selects the implementation family and resolves to
`<ip>/scripts/<manifest>.f`. For example, `vhdl` selects `vhdl.f` and `sv`
selects `sv.f`. The manifest name is not a testbench name.

`--tb <testbench>` selects one named `[tb:<testbench>]` section inside that
manifest. The runner compiles `[rtl]` plus the selected testbench section.
When `--tb` is omitted, the runner uses `DEFAULT_TB`, selects the only
testbench when exactly one exists, or reports an error when multiple
testbenches exist without a default.

```text
# Both platforms: <ip> <manifest> <tool>
run axis_fifo vhdl modelsim
run axis_fifo vhdl modelsim --tb basic
run axis_fifo vhdl modelsim --tb uvvm
run axis_fifo vhdl modelsim --tb uvvm project
run axis_fifo sv    modelsim --tb basic
run axilite_io sv   modelsim --tb default
run axi_monitor vhdl modelsim --tb traffic
run axis_fifo vhdl vivado project
run axis_fifo vhdl xsim gui

# Linux uses the same order
./run.sh axis_fifo vhdl modelsim --tb basic
./run.sh axis_fifo vhdl modelsim --tb uvvm project
./run.sh axilite_io sv modelsim --tb default
```

The launchers may accept either `vhdl` or `vhdl.f`, but the canonical internal
value is the manifest path. Windows and Linux must use the same positional
order: `<ip> <manifest> <tool>`.

Selection rules:

| Invocation | Meaning |
| --- | --- |
| `--tb name` | Run exactly `[tb:name]` |
| `--tb all` | Run every compatible testbench in the selected manifest |
| no mode | Run in `batch` mode |
| `gui` | Run in GUI mode when supported by the selected tool |
| `project` | Create or open the native project when supported by the selected tool |
| no `--tb`, `DEFAULT_TB` set | Select the named default testbench |
| no `--tb`, one TB, no default | Select the only testbench implicitly |
| no `--tb`, multiple TBs, no default | Error; the user must choose one |
| Vivado without `--tb` | Synthesize `[rtl] + [top] + [constraints:vivado]` |
| Vivado with `--tb` | Error; testbenches are not synthesis targets |

Vivado supports `batch`, `gui`, and `project` modes. With no `--tb`,
`project` creates or opens a Vivado project containing `[rtl]`, `[top]`, and
the selected constraints. `gui` may also create a Vivado project when the
backend requires one to open the IDE.

The existing command `run <ip> all [tool]` has a separate meaning: it runs
all manifest files for the IP. It must not be confused with `--tb all`, which
runs all testbenches within one selected manifest.

## 3. Syntax

### 3.1 Comments and whitespace

Comments begin with `#` and continue to the end of the line. Blank lines and
surrounding whitespace are ignored. Comments and manifest strings must remain
ASCII-only so the file can be consumed by CMD, Tcl, and shell tooling.

```text
# This is a comment
  # Indented comments are also valid
```

### 3.2 Global directives

Directives appear before the first section:

```text
DEFAULT_STD: 2008
DEFAULT_LIB: work
DEFAULT_TB: traffic
```

Supported directives:

| Directive | Meaning | Default |
| --- | --- | --- |
| `DEFAULT_STD` | VHDL standard for entries without `std=` | `2008` |
| `DEFAULT_LIB` | Local VHDL library for entries without `lib=` | `work` |
| `DEFAULT_TB` | Named testbench used when `--tb` is omitted | unset |

`DEFAULT_LIB` and `lib=` are optional for the first implementation. External
libraries such as UVVM are supplied by the simulator environment and must not
be remapped by blindly issuing `vmap` commands.

`DEFAULT_TB` is optional and must name an existing `[tb:<name>]` section. It
applies only to simulation. An explicit `--tb <name>` always takes precedence
over `DEFAULT_TB`; `--tb all` also overrides it and runs every compatible
testbench.

### 3.3 Reserved sections

Section names are not arbitrary. The runner understands this small vocabulary:

| Section | Meaning |
| --- | --- |
| `[rtl]` | Shared synthesizable and simulation sources |
| `[top]` | Synthesis top wrapper and synthesis-only sources |
| `[tb:<name>]` | One named simulation target |
| `[wave:<name>]` | Portable waveform view for a testbench |
| `[constraints:<tool>]` | Tool-specific constraints, such as Vivado XDC |

An unnamed `[tb]` section is not supported, even when it is the only
testbench. Use a named section such as `[tb:default]`; with exactly one
testbench, the runner then allows `--tb` to be omitted. Unknown sections are
validation errors. This prevents a typo such as `[tbb]` from silently changing
the build.

### 3.4 File entries

File paths are relative to the repository root (the directory containing
`run.py` and `tool_capabilities.ini`).

For example, in `axis_fifo/scripts/vhdl.f`:

```text
[rtl]
common/rtl/util_pkg.vhd
axis_fifo/rtl/axis_fifo.vhd        std=1993

[top]
axis_fifo/rtl/axis_fifo_top.vhd    std=2008

[tb:basic]
axis_fifo/tb/axis_fifo_tb_bfm_pkg.vhd   std=2008
axis_fifo/tb/axis_fifo_tb.vhd           std=1993
```

The supported file attributes are deliberately small:

| Attribute | Meaning |
| --- | --- |
| `std=` | Explicit VHDL standard: `1993`, `2008`, or `2019` |
| `lib=` | Explicit compile library |
| `tool=` | Simple allow-list, such as `tool=vivado,questa` |

Do not use `tb_top`, `feature`, or `exact_std` on file entries. Testbench
metadata belongs to its `[tb:<name>]` section, and standards are not silently
promoted.

### 3.5 Testbench sections

Each named testbench section contains metadata followed by its additional
sources. The runner compiles `[rtl]` first when that section is present, then
the selected testbench section.

```text
[tb:basic]
top = axis_fifo_tb
time_res = ps
requires =
wave = basic
axis_fifo/tb/axis_fifo_tb_bfm_pkg.vhd
axis_fifo/tb/axis_fifo_tb.vhd

[tb:uvvm]
top = axis_fifo_uvvm_tb
time_res = fs
requires = +uvvm
wave = uvvm
axis_fifo/tb/axis_fifo_uvvm_th.vhd
axis_fifo/tb/axis_fifo_uvvm_tb.vhd
```

Testbench metadata:

| Key | Meaning |
| --- | --- |
| `top` | Exact simulation entity/module to elaborate |
| `time_res` | Optional simulator resolution override, for example `ps` or `fs`; if omitted, the backend uses its default |
| `requires` | Comma-separated capability feature tokens, for example empty or `+uvvm`. Every token must be present in `tool_capabilities.ini` under `[features] allowed_features`. |
| `wave` | Optional name of the default `[wave:<name>]` view |

Only `top` is required for a simulation testbench. `time_res` is needed only
when the testbench depends on a particular simulator resolution. For example,
UVVM testbenches commonly use `fs`, while ordinary testbenches can omit the
override. The backend may apply a methodology-specific default when the value
is omitted.

If a manifest has exactly one named testbench, `--tb` may be omitted. If it has
more than one, omitting `--tb` selects `DEFAULT_TB` when declared; otherwise it
is an error. `--tb all` runs every compatible target.

### 3.6 Includes

Includes import a selected section from another manifest. The include path is
relative to the repository root. Entries inside the imported manifest are also
relative to the repository root, so all paths share one anchor.

```text
[rtl]
include axis_fifo/scripts/vhdl.f [rtl] std=2008
include parallel_prng/scripts/vhdl.f [rtl]

[tb:traffic]
include axi_mem_model/scripts/vhdl.f [rtl] std=2008
axi_monitor/tb/axi_monitor_tb.vhd
```

An include may force the VHDL standard of all VHDL files expanded from that
include:

```text
include common/scripts/shared.f [rtl] std=2008
```

The include-level `std=` override takes precedence over `DEFAULT_STD` and
`std=` attributes inside the included section. It applies only to VHDL files;
non-VHDL files are unaffected. Without an include-level override, each
expanded entry keeps the standard selected by its own manifest.

The initial implementation must support:

- section selection;
- include-level `std=` overrides;
- recursive includes;
- include-cycle detection;
- missing-manifest errors;
- ordered, deterministic expansion.

If the same source is included more than once with different effective
standards or library attributes, report an error rather than silently keeping
the first occurrence. An explicit include-level override is intentional and
must be applied before this conflict check.

## 4. Target Selection and Tool Behavior

The selected source closure is explicit. Absent sections contribute no files:

```text
simulation = [rtl, if present] + [tb:<selected-name>]
synthesis  = [rtl, if present] + [top, if present] + [constraints:<tool>]
```

Simulation and synthesis never compile all sections indiscriminately.

A simulation-only manifest may therefore be as small as:

```text
[tb:default]
top = axis_fifo_tb
requires =
axis_fifo/rtl/axis_fifo.vhd
axis_fifo/tb/axis_fifo_tb.vhd
```

This manifest cannot be used for synthesis because it has no `[top]` section.

### 4.1 ModelSim and Questa

Compile the selected ordered source list into the active local build library,
load the declared `top`, and run the simulation. In `gui` mode, load the
selected wave view in the GUI. In `project` mode, create or open the native
tool project and populate it with the selected source closure. UVVM libraries
remain external precompiled libraries configured by the simulator environment.

### 4.2 XSim

Use the same selected source closure where the language and capabilities are
supported. A target requiring `uvvm` or unsupported VHDL-2019 must be skipped
by `--tb all` and must produce a clear error when explicitly selected.

### 4.3 Vivado

Synthesis ignores all `[tb:<name>]` and `[wave:<name>]` sections. It uses
`[rtl]`, `[top]`, and the selected Vivado constraints section. A manifest with
no `[top]` is simulation-only and is skipped by synthesis. In `project` mode,
the backend creates or opens a Vivado project from that same synthesis source
closure; in `batch` mode, it performs non-project synthesis.

### 4.4 Standards and libraries

The runner passes each file's declared standard to the backend. It does not
promote VHDL-93 or VHDL-2008 to VHDL-2019. A backend may reject an incompatible
combination before compilation. This is important because the repository's
Questa flow can reject mixed standards during elaboration, while XSim support
depends on the installed Vivado version.

Local libraries may be created in the build directory. External libraries,
including precompiled UVVM libraries, are configured by the selected tool
environment and are not overwritten by the manifest runner.

## 5. Portable Wave Views

Waveform commands remain tool-specific, but ordinary signal selection is kept
tool-neutral. A wave view is associated with the selected testbench rather than
with an individual source file.

Example portable wave view:

```text
[wave:basic]
group = Clock_Reset
signal = aclk
signal = aresetn

group = Slave_Interface
signal = s_axis_tdata radix=hex
signal = s_axis_tvalid
signal = s_axis_tready

group = Master_Interface
signal = m_axis_tdata radix=hex
signal = m_axis_tvalid
signal = m_axis_tready

group = Status
signal = fifo_count radix=unsigned

group = DUT_Internal
signal = dut/r
```

The signal paths are relative to the selected top. A ModelSim backend prefixes
`/axis_fifo_tb/`; an XSim backend emits the equivalent syntax for its wave
tool. Supported portable attributes are initially `group`, `signal`, and
`radix`. Tool-specific path overrides are an escape hatch, not the normal
format.

The current `axilite_io` waveform selection maps naturally to another portable
view:

```text
[wave:default]
group = Clock_Reset
signal = clk
signal = rstn
signal = test_done

group = AXI4_Lite
signal = awaddr radix=hex
signal = awvalid
signal = awready
signal = wdata radix=hex
signal = wstrb radix=hex
signal = wvalid
signal = wready
```

## 6. Current Repository Examples

### 6.1 `axis_fifo`

The current repository has separate `vhdl.f` and `uvvm.f` lists. They can be
migrated into one `vhdl.f` containing `[tb:basic]` and `[tb:uvvm]` sections:

```text
# axis_fifo/scripts/vhdl.f
DEFAULT_STD: 2008
DEFAULT_LIB: work

[rtl]
common/rtl/util_pkg.vhd
axis_fifo/rtl/axis_fifo.vhd       std=1993

[top]
axis_fifo/rtl/axis_fifo_top.vhd

[tb:basic]
top = axis_fifo_tb
time_res = ps
requires =
wave = basic
axis_fifo/tb/axis_fifo_tb_bfm_pkg.vhd
axis_fifo/tb/axis_fifo_tb.vhd   std=1993

[tb:uvvm]
top = axis_fifo_uvvm_tb
time_res = fs
requires = +uvvm
wave = uvvm
axis_fifo/tb/axis_fifo_uvvm_th.vhd
axis_fifo/tb/axis_fifo_uvvm_tb.vhd
```

The existing `uvvm.f` remains a valid transitional manifest until this merge
is implemented and tested.

### 6.2 `axilite_io`

The repository has separate VHDL and SystemVerilog DUT flows. Keep those as
separate manifests because they select different RTL implementations:

```text
# axilite_io/scripts/sv.f
DEFAULT_STD: 2008
DEFAULT_LIB: work

[rtl]
axilite_io/rtl/axilite_io.sv

[tb:default]
top = axilite_io_tb
time_res = ps
requires =
wave = default
axilite_io/tb/axilite_io_wrap.sv
common/rtl/util_pkg.vhd
axis_fifo/rtl/axis_fifo.vhd
axilite_io/tb/axilite_io_harness.vhd
axilite_io/tb/axilite_io_th.vhd
common/rtl/axilite_bfm_pkg.vhd
axilite_io/tb/axilite_io_tb.vhd
```

This reflects the current `sv.f` order and its mixed-language wrapper
dependencies.

### 6.3 `axi_monitor`

The current `axi_monitor/scripts/vhdl.f` has two testbench entities in one
`[tb]` pool. Named sections make their dependency closures explicit:

```text
# axi_monitor/scripts/vhdl.f
DEFAULT_STD: 2008
DEFAULT_LIB: work

[rtl]
common/rtl/util_pkg.vhd
axis_fifo/rtl/axis_fifo.vhd
axilite_io/rtl/axilite_io.vhd
parallel_prng/rtl/xorshift128.vhd
axi_monitor/rtl/axi_monitor_ar.vhd
axi_monitor/rtl/axi_monitor_r.vhd
axi_monitor/rtl/axi_monitor.vhd
axi_monitor/rtl/axi_ar_gen.vhd

[top]
axi_monitor/rtl/axi_monitor_top.vhd
axi_monitor/rtl/axi_monitor_reg.vhd

[tb:traffic]
top = axi_monitor_tb
time_res = ps
requires =
parallel_prng/rtl/xorshift32.vhd
jitter_gen/rtl/jitter_gen.vhd
axis_latency_gen/rtl/axis_latency_gen.vhd
axi_mem_model/rtl/axi_mem_model_core.vhd
axi_mem_model/rtl/axi_mem_model.vhd
axi_monitor/tb/axi_monitor_tb.vhd

[tb:reg]
top = axi_monitor_reg_tb
time_res = ps
requires =
common/rtl/axilite_bfm_pkg.vhd
axi_monitor/tb/axi_monitor_reg_tb.vhd
```

The runner commands become unambiguous:

```text
run axi_monitor vhdl modelsim --tb traffic
run axi_monitor vhdl modelsim --tb reg
run axi_monitor vhdl vivado
```

## 7. Validation Rules

The parser must reject:

- missing files or manifests;
- unknown sections or attributes;
- duplicate directive keys;
- missing or duplicate `top` values in a selected testbench;
- a missing testbench selected by `--tb`;
- include cycles;
- paths escaping the allowed repository root;
- conflicting duplicate source attributes;
- unsupported standards or tool requirements;
- a requested mode that is not listed in the selected tool's `modes`;
- a `requires` token that is not in `[features] allowed_features` in
  `tool_capabilities.ini` (probable typo);
- synthesis requests without `[top]`.

The parser should preserve source order. Deduplication is allowed for an
identical canonical path with identical effective attributes. A path repeated
with a different library or standard is an error, not an opportunity to guess.

## 8. Migration Plan

1. Implement a parser for the current section syntax and repo-root-relative
   paths, with validation tests.
2. Add named `[tb:<name>]` selection to the ModelSim/Questa launcher.
3. Migrate one IP, preferably `axis_fifo`, from `vhdl.f` plus `uvvm.f` to a
   combined manifest and verify basic and UVVM simulations separately.
4. Add portable wave parsing and wave-view selection.
5. Update XSim and Vivado section filtering.
6. Migrate `axi_monitor` and mixed-language `axilite_io` using the examples
   above.
7. Update the repository README and IP README files after the launcher behavior
   is proven.

Generated committed scripts, tool-version comparison expressions, automatic
standard promotion, arbitrary section names, and automatic external-library
remapping are outside the first implementation.
